# 阶段 3 设计规格：主动决策与提醒引擎

日期：2026-09-24
状态：待用户审核书面规格；审核通过前不进入实现

## 背景与设计原则

阶段 1 已建立 PySide6 桌面壳，阶段 2 已交付本地 SQLite、Goal、Task、Memory、TaskService 与“今日任务”界面。阶段 2 的 `Task` 已包含 `due_date`、`planned_minutes`、`completed_units`、`target_units`、`hard_start`、`hard_end`、优先级和状态；目前没有软计划开始时间，任务界面也未提供计划时间输入。SQLite schema 版本为 1，`reminders` 表只是占位结构。

现有路线图把 Windows 活动监测列为阶段 3、学期日历列为阶段 4、LLM 列为阶段 5、Agent Decision Loop 列为阶段 6。此规格将确定性决策核心前置为新的阶段 3；原阶段 6 的规则型 Decision Loop 由本设计取代。Windows 全面活动监测不再是阶段 3 的前置条件，暂缓到后续独立阶段。原阶段 4、5 和语音/打包阶段保持为后续工作，具体编号在实施计划阶段再统一调整。

核心原则是**宁可安静，也不在错误时机打扰**。提醒需要有可解释的任务风险依据、满足活动状态和冷却门槛，并且一次只呈现一个建议。硬时间边界永远不因提醒、延期或自然语言输入而改变。

## 目标

- 以当前时间、当天计划、优先级、硬时间边界、剩余工作量、进度、关联长期目标、活动状态和提醒历史，确定是否现在提醒、等待或保持安静。
- 对“原定时间已到”与“现在适合打断”分别判断，避免只按时钟机械弹窗。
- 在无 LLM、无 Qt、无真实系统时钟和无 SQLite 的情况下运行完全确定、可重复的规则决策。
- 为“现在做、稍后、延长 X 分钟、今天跳过、已完成”定义稳定语义，并在延期后重新运行完整决策。
- 将决策、用户动作和数据持久化边界清楚分开，便于使用 fake clock、fake repository 和 fake activity source 测试。

## 非目标

- 不实现 LLM 提醒判断、自然语言理解、人格生成或云端 provider。
- 不实现 Windows 全面活动监控、进程/窗口采集、键鼠监控、语音、TTS 或自动习惯学习。
- 不实现课程表、复杂时间自动规划、跨设备同步或自动重排任务。
- 不允许决策引擎自行修改 `hard_start`、`hard_end`、`due_date`、计划分钟或任务优先级。
- 不要求 Stage 3 推断用户正在使用哪个具体应用或语义上做什么；活动状态只提供粗粒度 idle/focused/unknown。

## 核心领域模型

### Task 与 Goal

Stage 3 为 `Task` 增加可选的 `planned_start_at: datetime | None`，作为软计划开始时间。它与 `hard_start`、`hard_end` 不同：到达软计划时间只是决策的一个信号，不构成必须开始或完成的约束。该字段保存为带时区的时间并规范化为 UTC；现有任务迁移后为 `NULL`。任务界面需允许用户填写本地日期和时间，应用层通过明确的时区转换保存。

`due_date` 仍是本地日历日期，用于当天任务和逾期任务归集；它不伪装成精确到分钟的硬截止。`hard_start` 表示最早可开始时间，`hard_end` 表示最晚完成时间。提醒引擎不得覆盖二者。

剩余工作分钟数确定性计算：无数量目标时等于 `planned_minutes`；有数量目标时为 `ceil(planned_minutes × max(target_units - completed_units, 0) / target_units)`；剩余单位为零或任务已完成时剩余分钟为零并排除提醒候选。该估算只用于本地排程，不被记录为实际耗时。

任务只使用其关联 Goal 的 `active` 和 `priority`。Goal 已停用或不存在的任务仍保留在任务界面，但不参与主动提醒。Goal 优先级只用于任务优先级、截止风险和软计划时间仍相同时的稳定排序，不得单独把低优先级任务提升为打断理由；Stage 3 不解析 Goal 文本含义。

### ActivitySnapshot

定义无 UI 依赖的最小活动快照：

- `state`: `idle | focused | unknown`
- `observed_at`: 最近一次观测的 aware UTC 时间
- `state_since`: 当前连续状态开始时间；状态切换时重置

`focused` 只表示用户持续活跃、可能正在做另一件事，不表示具体应用或活动内容。连续专注时长由 `now - state_since` 计算。快照超过 2 分钟未更新、来源报错或时间无效时，应用层将其降级为 `unknown`。Stage 3 不读取应用名、窗口标题、键盘内容或屏幕画面。

### ReminderPreferences 与状态

偏好至少包含主动提醒开关、安静时段、全局最小间隔、同任务间隔和默认稍后时间。默认值：安静时段 22:00–08:00、本地全局提醒间隔 10 分钟、同任务普通提醒间隔 30 分钟、“稍后”15 分钟。上述设置可由用户配置，但必须经过范围校验。

每个任务、每个本地日期保存 `TaskReminderState`：最近动作、下次评估时间、延期次数、最后展示时间以及当日跳过状态。全局保存最近一次卡片展示时间。`ReminderEvent` 只记录事件类型、任务 ID（可空）、UTC 时间、本地日期、原因码和幂等键，不保存自然语言文本。

### Decision

纯规则引擎输出以下结构之一：

- `SHOW_REMINDER`：一个任务 ID、提醒类别、稳定原因码、展示模式和生成时间。
- `WAIT`：不展示，附原因码和建议的 `next_evaluate_at`。
- `SILENT`：当前没有可安全展示的提醒；可附下一次有意义的评估时间或不设时间（例如提醒总开关关闭）。

原因码使用稳定枚举，例如 `NO_ELIGIBLE_TASK`、`BEFORE_PLANNED_START`、`HARD_START_NOT_REACHED`、`DEADLINE_RISK`、`PLAN_OVER_CAPACITY`、`FOCUS_GRACE`、`IDLE_USER`、`ACTIVITY_UNKNOWN`、`QUIET_HOURS`、`GLOBAL_COOLDOWN`、`TASK_COOLDOWN`、`USER_SNOOZE`、`EXTENSION_DUE`、`SKIPPED_TODAY`、`REMINDERS_DISABLED`。UI 不自行推导原因或优先级。

## 决策输入与时间边界

应用服务每次调用引擎时组装完整的 `DecisionContext`：

- 由 `Clock` 提供的 aware UTC `now`；显式提供本地日期、IANA/系统时区标识和本地时刻，不由领域层读取系统时间。
- 当天和逾期候选 Task 的不可变快照，以及它们关联的 Goal 状态和优先级。
- `ActivitySnapshot`，包含状态、观测时间和状态持续起点。
- 对应本地日期的任务提醒状态、全局最近展示时间和提醒偏好。
- 当前应用运行状态若可用；不可用时不能假设用户空闲。

领域决策代码禁止直接调用 `datetime.now()`、`date.today()`、系统 API、Qt、sqlite3 或网络接口。应用层可以实现真实 Clock；新建/更新时间由应用服务显式传入 Clock 提供的时间，不能在决策和提醒核心中隐式读取系统时间。测试使用可设定和推进的 fake clock。持久化 UTC 瞬间与本地日期键分开处理。夏令时无效或歧义的用户输入时间必须由界面明确处理，不能静默猜测；安静时段按显式时区下的本地墙上时间计算。

## 候选筛选、优先级与冲突解决

仓储需要提供 `due_date <= local_date` 的开放任务，以及 `planned_start_at` 落在今天的开放任务。候选必须满足：任务未完成、数量目标尚有余量、关联 Goal 仍 active、尚未被“今天跳过”、当前不是 `hard_start` 之前。逾期任务仍可候选，但会带有逾期原因；未来日期且没有今天软计划时间的任务不参与今天的决策。

软计划时间达到后给予 5 分钟宽限。若设有 `planned_start_at`，在 `planned_start_at + 5 分钟` 前不因软计划时间触发提醒。若没有软计划时间，不因 `due_date` 是今天就立即提醒；只有当剩余可用时间已不大于剩余估算分钟，或当天剩余开放任务总分钟数超过可用时间时，才形成时间风险信号。

可用工作窗口截至以下时刻中最早者：当前本地日的安静时段开始时间、未来的 `hard_end`。若 `hard_start` 在未来，可用窗口从该时间开始。已过的 `hard_end` 标记为逾期，不再被描述为可按时完成；任务可作为普通逾期工作候选，但延期请求不得跨越或“刷新”这个硬边界。引擎不会把一天的时间预算当作确定承诺，只用它判断计划是否拥挤。

每天剩余工作量超出至安静时段前的剩余分钟数时，产生 `PLAN_OVER_CAPACITY` 信号。这是粗略风险信号，不承诺任务一定能按分钟完成。未来硬截止的 slack 定义为 `hard_end - max(now, hard_start) - remaining_minutes`；负数表示按当前估算已无法在截止前完成，零到 30 分钟表示可挽回但余量很小。稳定排序顺序为：

1. 仍可挽回且 slack 最小的未来 `hard_end` 风险；逾期硬截止任务排在可挽回风险之后。
2. Task 优先级 P0、P1、P2。
3. 最早的软计划开始时间；缺失时间排在有时间的任务之后。
4. Goal 优先级 P0、P1、P2，仅作平局裁决。
5. 创建时间，再按 Task ID，保证完全稳定。

每轮先为每个候选任务计算风险与当前状态下是否满足展示门槛，再从可展示的候选中按上述顺序选一个，避免一个当前不能打扰的 P2 任务挡住可提醒的 P0/P1 任务。若没有任务满足展示门槛，返回最早的有效等待条件。低优先级任务不能仅凭计划时间覆盖更高优先级的、同样可提醒任务；只有更早且仍可挽回的硬截止风险可以优先。

## 打扰与保持安静的规则

按以下顺序门控；前面的绝对静默规则优先于后面的打断资格：

1. 主动提醒关闭、处于安静时段、没有候选任务或所选任务被跳过时，返回 `SILENT`。
2. `idle` 时不前台弹卡，返回等待；下次用户恢复活跃时重新评估。
3. `unknown` 按“不能确认用户可被打扰”处理。普通任务保持安静；仅当 P0 任务有未来硬截止、硬截止距现在不超过 30 分钟且剩余工作按估算仍能在截止前完成时，允许无声音、非模态卡片。
4. `focused` 少于 120 分钟时通常等待。唯一例外为符合上一条同等紧急度条件的 P0 硬截止任务，可显示无声音、非模态卡片。
5. `focused` 达到 120 分钟或更久时，只有 P0/P1 且满足以下至少一项才可提醒：软计划时间已迟到至少 30 分钟、硬截止已进入风险窗口、或当天剩余计划超出可用时间。P2 在用户持续专注时不打断。

提醒开关和安静时段是绝对的用户控制，即使 P0 也不弹窗。引擎返回 `WAIT` 时必须提供下一次有意义的唤醒时机，例如计划宽限结束、专注 120 分钟、用户稍后/延期到期、冷却结束或本地安静时段结束。应用运行时每分钟检查一次，并在启动、活动状态变化、任务变化、用户动作和 `next_evaluate_at` 到达时立即重评。

## 提醒生命周期与用户动作

生命周期为：候选 → 规则评估 → 展示或等待/静默 → 用户动作或卡片关闭 → 状态持久化 → 到期/任务变化/活动变化时重新评估。展示前先以事务写入展示事件和冷却时间，再通知 UI；写入失败时不展示，以免进程重启后重复弹出。卡片关闭只记录已看过并应用普通冷却，不等于“稍后”或“今天跳过”。

- **现在做**：记录确认，压制同任务的普通重复卡 30 分钟，30 分钟时重评。它不自动启动其他应用，也不自动将任务标记完成。
- **稍后**：记录 snooze，默认 15 分钟后重评；若后续开放偏好设置，允许用户调整该时长。
- **延长 X 分钟**：X 为 1–120 的整数，每任务每本地日最多接受一次。接受前校验用户指定的重评时刻、剩余估算工时、`hard_start`、未过期 `hard_end` 和安静时段；若 `max(now + X, hard_start（若有）) + remaining_minutes` 晚于可用边界则拒绝，并说明原因。延期只记录一次性 `extension_deadline`，绝不改写原硬时间。到期后从当前任务和当前状态重新调用完整引擎；到期本身不保证再展示。
- **今天跳过**：仅对该任务、当前注入的本地日期生效，到下一个本地日期自动失效。跨午夜重启后按新的日期键决定，不把它解释为永久忽略。
- **已完成**：通过现有 TaskService 完成无数量目标任务，或将数量任务标记完成；成功后记录动作并立即重评下一个候选。服务失败时不得记录完成事件，也不得显示成功状态。

延期的显式重评时间优先于普通同任务间隔，但仍重新检查提醒总开关、安静时段、活动门控和全局 10 分钟最小间隔。若全局间隔尚未结束，在延期时间先运行决策并返回 `WAIT(GLOBAL_COOLDOWN)`，冷却结束时再次重评。这样保留用户要求的重评点，同时避免跨任务连续弹卡。

## 冷却与重复控制

全局 10 分钟间隔约束所有主动卡片；同任务 30 分钟间隔约束普通重复卡。`稍后`的用户指定时间作为该任务明确重评时间。接受延期按用户指定期限重评。展示、动作和任务完成均使用幂等键；重复点击、调度器重入或应用重启不得重复接受延期、重复写事件或反复展示同一决策。优先检查任务完成、日期变化、活动快照新鲜度和提醒偏好，再处理冷却，避免向已完成或已关闭提醒的任务展示陈旧卡片。

## 架构与持久化变更

依赖方向保持 `domain ← application ← desktop/infrastructure` 的既有边界：

- 纯领域模块提供 `decide(context) -> Decision` 和确定性估算/排序函数。
- Ports 提供 `Clock`、`ActivitySource`、任务/目标读取、ReminderState/Preferences 存取接口；Domain 不依赖任何适配器。
- 应用层 `ProactiveReminderService` 读取快照、组装上下文、调用引擎、保存展示/动作并安排重评；UI 只订阅其结构化结果。
- TaskService 扩充软计划开始时间读写和按日期范围列出候选任务的用例；业务校验仍在应用/领域层，不放入 SQLite repository。

SQLite 使用新的 schema version 2 追加迁移，不能改写已经发布的 v1 迁移，也不删除或复用当前占位 `reminders` 表。v2 设计新增：

- `tasks.planned_start_at` 可空 UTC 时间列；现有数据为 NULL。
- 按 `(task_id, local_date)` 唯一的提醒任务状态表，存储用户动作、重评 UTC 时间、当天延期次数、展示时间和跳过状态。
- 单行全局提醒运行状态，存储最近卡片展示 UTC 时间。
- 追加式提醒事件表，保存任务引用（删除任务时置空）、本地日期、UTC 时间、事件类别、原因码和唯一幂等键。
- 偏好复用 v1 `settings` 普通设置表的命名空间键，并经类型化 Preferences 接口验证；不存任何凭据。

写入状态和事件必须处于同一事务。Repository 只负责查询、约束、事务和错误转换，不选择任务、不计算优先级、不判定是否打扰。schema v2 迁移失败时保持数据库回滚到 v1，并停用主动提醒；任务与其他桌面功能继续可用。

## UI 交互

任务编辑界面增加可选的本地软计划开始时间。提醒卡展示任务标题、P0/P1/P2、关联目标、原计划时间（若有）、迟到时间、剩余分钟估算和简短规则理由。规则理由由应用层的本地模板映射原因码生成；Stage 3 不调用 LLM 改写或决策。

卡片提供“现在做”“稍后”“延长 X 分钟”“今天跳过”“已完成”。“延长”提供分钟输入和有效范围；校验失败时保留卡片并显示具体边界原因。卡片不能遮挡键盘焦点或强制抢焦点；可用时优先非模态桌面卡片。安静时段绝不展示提醒卡。

## 故障处理与隐私边界

- 活动来源失败或过期：降级为 `unknown`，按未知状态的门控规则保持安静。
- SQLite 迁移/读取/写入失败：主动提醒停止工作并向用户显示本地存储不可用；任务界面仍可独立报告其数据状态。不得用未持久化的临时状态继续弹窗。
- TaskService 完成操作失败：保留提醒上下文并给出可理解的操作失败提示，不伪造完成事件。
- 时钟或时区上下文无效：该轮返回静默/等待并记录稳定错误码，不猜测本地日期，不生成卡片。
- 调度器异常：保持应用可用，记录不含任务正文的错误码，并在下一次正常唤醒重试；无无限快速重试。
- 本地库仅保存任务关联 ID、时间、动作类型和原因码。Stage 3 不上传提醒/活动数据，不采集应用名、窗口标题、按键、屏幕内容或对话原文；日志不写任务标题、目标内容或用户自由文本。

## 测试策略

领域测试使用构造的 Task/Goal/ReminderState、fake clock 和纯函数输入，覆盖：

- P0/P1/P2 稳定排序、Goal 平局裁决、逾期与停用目标排除、同一任务 ID 的稳定结果。
- 软计划时间 5 分钟宽限、无计划时间时按剩余可用时间触发、硬开始未到、硬截止可挽回/已过、数量进度对剩余分钟的影响。
- 当晚剩余总工时与可用分钟的过载判断，以及 P0/P1/P2 对 focused/idle/unknown 的门控。
- 22:00–08:00 安静时间、提醒关闭、连续专注 119/120 分钟、过期 ActivitySnapshot、空闲恢复后的重评。
- 全局和单任务冷却、稍后、当天跳过、一次/日延期、延期过长拒绝、延期截止后完全重评，以及任务完成后转向下一个候选。
- UTC/本地日期换日、夏令时跳变/歧义输入和注入时区边界。

应用服务测试使用 fake repositories、fake clock、fake ActivitySource，验证调度唤醒、提交先于展示、操作幂等、完成失败不落成功事件、数据库故障停用主动卡片、一次只展示一个任务。SQLite 测试使用临时数据库，覆盖 v1→v2 迁移、回滚、重启恢复、外键行为、UTC 序列化和事件/状态原子事务。UI 测试只验证结构化决定正确展示、动作参数正确交给应用服务、Qt 层不含决策规则。

## 验收标准

1. Decision Engine 对相同 context 始终返回相同 Decision，且模块导入不需要 Qt、Windows API、sqlite3 或网络依赖。
2. 使用 fake clock 和 fake repository 可以完整测试决策、延期、跳过、冷却及重启恢复。
3. 19:30 软计划时间单独到达不会必然弹窗；20:10 时若用户已连续 focused 130 分钟，引擎根据晚间可用分钟、候选任务剩余分钟、P0/P1/P2 和硬截止选择一张卡或继续等待/安静，并返回可解释原因码。
4. 只有日期到期但没有软计划、风险或过载信号的任务，不会仅因日期到了立即弹窗；完成、停用 Goal、静默时段、关闭提醒和 idle 状态都遵循明确门控。
5. 用户延长 30 分钟后保存一次延期事件和期限；30 分钟后对更新后的任务/进度/活动/安静时段重新执行完整决策。决策可以展示、等待或静默，不能保证重复原卡。
6. 同任务每日最多接受一次、最长 120 分钟的延期；任何延期都不改变 `hard_end`，不允许越过未过期硬截止或安静时段的可用边界。
7. “今天跳过”在注入的本地日期结束时失效；时间戳仍以 UTC 持久化；跨午夜、重启和 DST 用例均由测试覆盖。
8. 每轮至多一张提醒卡；冷却生效；重复动作与调度不会产生重复事件或弹窗。
9. schema v2 在 v1 上以追加迁移方式成功升级；失败可回滚，v1 reminders 占位数据结构不被破坏。
10. 数据库故障时主动提醒关闭但桌面应用保持可用；日志、数据库事件和网络流量均不包含未授权活动细节或自由文本。
